# Auth Module

## 1. Module Overview
The Authentication module provides the entry points for external actors to authenticate into the system. It handles user registration via secure password hashing and issues stateless JSON Web Tokens (JWT) for subsequent authenticated and authorized (RBAC) requests.

## 2. Database Schema
*The Auth module does not have a dedicated internal schema. It operates directly upon the `userTable` defined in the **User Module**.*

- The module relies on inserting new users and checking usernames/passwords natively against the `userTable`.
- Password hashes are stored safely via Bun's native `Bun.password.hash` with Argon2id.

## 3. Relations to Other Modules
- **User Module**: Deeply coupled. Auth relies on User schemas and services (`createUser`, `getUserByUsername`) to execute its login and registration logic.
- **RBAC Module**: Once authenticated, tokens generated by the Auth module expose the user's identities safely into the system, which RBAC utilizes down the line to check `hasPermission` grants.

## 4. API List with Request and Response Examples

### `POST /auth/register`
Creates a brand new user account directly accessible by the public. Passwords uploaded here will be securely hashed before persistence.

**Request Body:**
| Field | Type | Rules |
|---|---|---|
| `name` | string | min 2 characters |
| `username` | string | min 3 characters |
| `password` | string | min 6 characters |

**Request Example:**
```json
{
  "name": "Jane Doe",
  "username": "jane",
  "password": "strongPassword123"
}
```

**Response Example (201 Created):**
```json
{
  "id": "e8d98d25-9b88-4447-b8a5-d06efce2123d",
  "name": "Jane Doe",
  "username": "jane",
  "createdAt": "2026-02-21T15:00:00.000Z",
  "updatedAt": "2026-02-21T15:00:00.000Z"
}
```
*(Notice the `password` property is intentionally omitted from the return payload for security).*

**Error Responses:**
- `400 Bad Request` — Username is already registered (`"Username already registered"`).

### `POST /auth/login`
Authenticates a user via username and password combination. Returns a JWT token valid for 24 hours that must be passed as `Authorization: Bearer <token>` in subsequent requests.

**Request Example:**
```json
{
  "username": "jane",
  "password": "strongPassword123"
}
```

**Response Example (200 OK):**
```json
{
  "user": {
    "id": "e8d98d25-9b88-4447-b8a5-d06efce2123d",
    "name": "Jane Doe",
    "username": "jane",
    "createdAt": "2026-02-21T15:00:00.000Z",
    "updatedAt": "2026-02-21T15:00:00.000Z"
  },
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}
```

**JWT Payload:**
- `sub` — the authenticated user's UUID (used by RBAC middleware to identify the actor)
- `exp` — Unix timestamp set to 24 hours from token issuance

**Error Responses:**
- `401 Unauthorized` — Username not found or password does not match (`"Invalid username or password"`).

## 5. Lecturer Q&A (Showcase Preparation)

**Q1: Why did you choose JWT instead of normal website sessions?**
**Answer:** JWTs are really easy to use with APIs. The server doesn't have to remember who is logged in. It just checks if the token the user sent is valid. This makes our backend faster and simpler to run.

**Q2: How does the system know what I'm allowed to do after I log in?**
**Answer:** When you log in, the server gives you a token. Then, when you try to do something (like add a stock), a "middleware" checks that token, finds your User ID, and looks up in the database if your role has the right permission to do that action.

**Q3: Are the passwords safe in the database?**
**Answer:** Yes, we don't save the real passwords. We use a built-in tool in Bun to "hash" the passwords before saving them. So even if someone looks at the database, they just see random letters and numbers, not the real password.

**Q4: Can anyone register a new account on the public page?**
**Answer:** Yes, the `/auth/register` is open so normal employees can sign themselves up. But to get special powers (like Admin), an existing admin has to log in and update their role in the system.
